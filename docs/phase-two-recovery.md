# حفظ التنفيذ واستئنافه

## التخزين والترحيل

- التخزين الأساسي للمهام والمشاريع والجداول ونقاط الاستئناف هو `data/manus.db`، باستخدام SQLite المضمّن في Node (يتطلب Node 22.13 أو أحدث).
- يستخدم WAL و` synchronous=FULL`، وتُكتب التغييرات فورًا. اكتمال المهمة وحفظ جوابها وحذف نقطة الاستئناف معاملة واحدة.
- في التشغيل الأول تُستورد `data/db.json` في معاملة واحدة، ويظل الملف الأصلي كما هو، مع نسخة `data/db.pre-sqlite.json`. لا يُعاد الاستيراد بعد نجاحه. JSON غير صالح يمنع التشغيل برسالة خطأ ولا يُستبدل بقاعدة فارغة.
- لا تُحذف المهام تلقائيًا بعد بلوغ 300 مهمة. بيانات كل كيان محفوظة كـJSON داخل SQLite؛ هذه المرحلة لا تضيف فهرسة نصية أو ترحيلًا لتخزين الذاكرة الدلالية.
- عند بدء التطبيق تُنشأ نسخة SQLite متسقة لليوم في `data/backups/` إن لم توجد نسخة لذلك اليوم. لا تُحذف النسخ القديمة تلقائيًا.
- يمنع سجل ملكية العملية تشغيل خادمين على مجلد البيانات نفسه. بعد موت العملية يمكن للخادم الجديد استلام الملكية.

## الاستئناف

تتحول المهام التي كانت `running` أو `queued` عند الإقلاع إلى `interrupted`. لا يبدأ أي منها تلقائيًا. افتح المهمة واضغط **استئناف المهمة**.

تُحفظ الخطة والخطوات المقبولة والأدلة والناتج الأخير وعدادات المحاولات والاستهلاك. يبدأ الاستئناف عند الخطوة التالية، دون إعادة الخطوات المكتملة. يحتفظ بالسياق والنموذج والوضع ومساحة العمل؛ يجب اختيار مساحة العمل الأصلية قبل الاستئناف.

إذا انقطع التطبيق داخل خطوة، فقد يكون إجراء خارجي قد نُفّذ قبل حفظ النتيجة. يعرض الزر تنبيهًا ويطلب تأكيد **إعادة محاولة الجزء غير المكتمل**. راجع الملفات أو النظام الخارجي قبل التأكيد. هذه آلية منع إعادة تشغيل عمياء، وليست ضمان تنفيذ الإجراءات الخارجية مرة واحدة تمامًا. النمط الخطي القديم لا يملك نقاط حفظ لكل خطوة؛ استئنافه بعد بدء التنفيذ يعيد الطلب بعد التأكيد.

تظل حالات الفشل والإلغاء قابلة للاستئناف حين توجد بيانات تنفيذ محفوظة. إرسال طلب جديد للمهمة يبدأ دورة جديدة ويستبدل نقطة الاستئناف السابقة.

## الطابور والموارد

هناك تشغيل واحد نشط لكل خادم، بترتيب الوصول. المهام اليدوية والمجدولة والتقييمات تشترك في الطابور؛ هذا يمنع تشغيل مهمتين على المتصفح وسطح المكتب المشتركين في الوقت نفسه. يحتفظ التشغيل بملكية الموارد حتى يخرج فعليًا، حتى بعد طلب إلغائه. إلغاء مهمة منتظرة يحذفها من الطابور دون إلغاء التشغيل النشط.

هذه الحماية بين تشغيلات المهام والتقييمات داخل العملية؛ لا تعزل برامج المستخدم أو التحكم اليدوي المباشر، ولا تعيد إنشاء جلسات PTY والمتصفح القديمة بعد إعادة التشغيل. لا تُطلق الجدولة تكرارًا جديدًا إذا كانت مهمتها السابقة منتظرة أو نشطة أو منقطعة.

## الواجهات والاختبار

- `GET /api/queue`: المهمة النشطة ومعرّفات المنتظرة.
- `GET /api/tasks/:id`: يضيف `recovery` مع إمكانية الاستئناف وعدد الخطوات المقبولة وضرورة تأكيد إعادة المحاولة.
- `POST /api/tasks/:id/resume`: يستأنف الطلب المحفوظ. يرفض الخطوة غير المحسومة بـ409 ما لم تُرسل `{ "retryInterruptedStep": true }` بعد تأكيد المستخدم.
- `npm run verify`: فحص الأنواع والترميز والتقييم والمنسق وترحيل SQLite والتعافي والطابور.
- `npm run check:recovery:http`: يشغّل خادم التطبيق مع نموذج HTTP محاكى، يقتل العملية ويعيد تشغيلها، ثم يتحقق من الاستئناف وعدم تكرار كتابة الملف المكتمل ومن عزل إلغاء المهام المنتظرة.

اختبارات التعافي تستخدم مجلدات مؤقتة ولا تُرحّل بيانات المستخدم الفعلية. الترحيل الفعلي يحدث عند تشغيل الإصدار الجديد. لا تشغّل إصدار JSON القديم بالتزامن مع هذا الإصدار.

لاستعادة نسخة احتياطية: أوقف التطبيق، واحفظ مجلد البيانات الحالي كاملًا، ثم ضع نسخة SQLite المتسقة في مجلد بيانات جديد باسم `manus.db` وشغّل التطبيق على ذلك المجلد. استخدم مجلدًا جديدًا لتجنب خلط ملف النسخة مع ملفات WAL قديمة. حافظ أيضًا على مساحة العمل والذاكرة والمهارات؛ نسخة قاعدة المهام لا تحتوي ملفاتها.
