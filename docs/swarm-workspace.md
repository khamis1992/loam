# مساحة ذكاء الأسراب وشركة البرمجيات

افتح `/#/studios/swarm` من Loam. اكتب موجز المنتج ومعايير القبول، واختر نموذجًا متاحًا من خادم Ollama، ثم ابدأ الفريق. تستخدم هذه المساحة تنفيذًا فعليًا عبر `runAgent` وأدوات الملفات والأوامر؛ لا تستدعي مولدات MiroFish أو قوالب Frontier القديمة.

## دورة العمل

1. اكتشاف المنتج: وثيقة منتج بمستخدمين ورحلات وقصص استخدام مرقمة بمعايير قبول وخريطة إصدارات — ببوابة ترفض الناقص وتسميه.
2. تصميم التجربة: عقد تصميم ببنية معلومات ونظام عربي RTL وحالات فراغ/تحميل/فشل وملاحظات إتاحة — ببوابة مماثلة. مخرجات المرحلتين تُلزم التنفيذ والمراجعة والاختبارات المستقلة.
3. المتطلبات: نطاق المنتج ومعايير القبول.
4. البنية وتحليل المخاطر وتحليل المستودع القائم: تعمل بالتوازي عند السماح، ويتلقين تقرير المتطلبات. عند وجود كود قائم (أو مستودع مزروع عبر `repoSeed`) يحلله وكيل قراءة فقط مستندًا إلى فهرس المشروع؛ وفي المشاريع الجديدة تُكمل هذه المرحلة حتميًا دون استدعاء نموذج.
5. التنفيذ: يكتب المصدر والاختبارات داخل مجلد المهمة المستقل؛ وعند وجود مستودع قائم يعدّله أدنى تعديل يحترم أعرافه.
6. مراجعة الكود: دور قراءة فقط يطابق الملفات الفعلية مع البنية ومعايير القبول، وينهي إجابته بـ`REVIEW_PASS` أو `REVIEW_ISSUES` مع قائمة موانع مرقمة.
7. اختبارات قبول مستقلة: دور **لم يكتب التنفيذ** يحوّل معايير القبول وكل مانع مراجعة إلى ملفات `node:test` جديدة؛ لا يملك صلاحية كتابة إلا ملفات الاختبار، ولا يجوز له تعديل المصدر. إن تعذّر اختبار المشروع بـnode:test ينهي بـ`INDEPENDENT_TESTS_NA` مع السبب.
8. الجودة: تقرأ الملفات وتشغّل أوامر تحقق فعلية. لا تكفي إجابة النموذج لإثبات النجاح. **ثم ينفّذ المحرك نفسه مجموعة الاختبارات المستقلة كبوابة حتمية** لا تمر عبر أي نموذج: فشلها يعيد التشخيص إلى التنفيذ ضمن جولات الإصلاح.
9. التسليم: ملفات فعلية، وطريقة تشغيل، ودليل التحقق، ونتيجة الاختبارات المستقلة، وجولات الإصلاح، والقيود.

كل وكيل يتلقى نتائج المراحل السابقة. المراحل التحليلية والمراجعة تملك أدوات قراءة فقط؛ مؤلف الاختبارات يملك القراءة وكتابة ملفات الاختبار حصرًا؛ التنفيذ يملك الكتابة وتشغيل الأوامر؛ الجودة تملك القراءة وتشغيل الأوامر. لا توجد أرقام جمهور أو نتائج محاكاة مفترضة.

### دروس الإخفاقات وحماية الوكلاء

تفشل العملية ← يسجل المحرك درسًا معقمًا في `data/swarm/lessons.md`، وتستقبل العمليات الجديدة في مطالباتها الدروس المتقاطعة مع موجزها. وقبل التسليم يمسح المحرك الملفات المسلَّمة بحثًا عن تعليمات خبيثة موجهة للوكلاء (بوابة صارمة) وعن ملاحظات أمنية استشارية (مسارات بلا مصادقة، تركب SQL/shell من مدخلات، رفع بلا ترشيح) تُسجل في تقرير الأمن.

### الفرق الفرعية المتوازية (مسار الويب)

عمليات مسار الويب تنفّذ بفريقين متوازيين: فريق الخدمات (الخادم والوحدات والاختبارات) وفريق الواجهة (`public/` فقط)، بملكية ملفات مفروضة على مستوى الأدوات — لا يستطيع فريق الكتابة في منطقة الآخر. مرحلة المراجة تعمل منسّق تكامل بينهما. وإخفاقات الاتصال أثناء التحقق (ECONNREFUSED وأخواتها) تُعامل كبنية تحتية لا كفشل توكيد، فلا تحجب نجاحًا لاحقًا.

### البحث والقرارات المشتركة

تُحقن في مطالبات أدوار العمل نتائج بحث فوق فهرس المشروع مشتقة من موجز العملية (مسارات وأنواع ومعتمدون)، ويحتفظ المحرك بسجل قرارات مشترك `.loam/swarm/decisions.json`: أي مرحلة تسجل اختيارًا بسطر يبدأ `DECISION:` يُحلَّل حتميًا ويصل لكل المراحل اللاحقة. وبتفعيل `LOAM_SWARM_SANDBOX=auto` مع Docker متاح تُنفَّذ فحوص النشر والدمج داخل حاوية `node:22-alpine` (تشغيل حي مثبت؛ أطلِق Docker Desktop أولًا).

### فروع الكود وطلبات المراجعة والدمج

لكل عملية فرع مستقل `swarm/<id8>` على مستودعها، ويمكن إنشاء عملية جديدة فوق تسليم عملية سابقة عبر مدخل `baseRun` (استنساخ المستودع والتفرع من وسم pre-deploy). في نهاية الدورة تُكتب المرحلة الحتمية «الدمج وطلب المراجعة» كائنَ طلب مراجعة في `.loam/swarm` (الفرع والأساس والملفات المتغيرة وكل أدلة التحقق)، ثم تدمج الفرع إلى main بحل تعارضات أساسي معلن، وتعيد تشغيل أمر التحقق والاختبارات المستقلة على الشجرة المدموجة — فكسر تعديلات سابقة يفتح جولة إصلاح. كذلك يخصص الفريق تعليماته بحسب طبيعة المشروع تلقائيًا (web/api/library/mobile/desktop/ai بمدخل `track` أو كشف من الموجز — لكل مسار عقد بناء وتحقق مناسب: مكوّنات جوال RTL، وحدات سطح مكتب بأسلوب Electron، أو وحدة ذكاء اصطناعي حيادية المزود بمستجيب محقون)، ويمكن تفعيل تنفيذ معزول بحاويات عبر `LOAM_SWARM_SANDBOX=auto` عند توفر Docker/Podman.

### تجهيز النشر والمعاينة

بعد التسليم تُكمل المحرك مرحلة «تجهيز النشر» حتميًا: اكتشاف نقطة تشغيل المنتج، فحص صحة فعلي (إقلاع واستطلاع HTTP لمنتجات الخدمة، أو مجموعة الاختبارات للمكتبات)، وكتابة حزمة `deploy/` بسكربتات تشغيل وبيان يحوي أمر تراجع مدعومًا بوسم git فعلي (`git reset --hard pre-deploy`). المنتجات الخدمية السليمة يمكن تشغيلها معاينةً من الواجهة (زر «تشغيل معاينة المنتج») عبر نقطتي preview/preview/stop على 127.0.0.1.

### ذاكرة المشروع المفهرسة

يبني المحرك فهرسًا لكل عملية من ملفاتها الفعلية: تصنيف الملفات (كود/اختبارات/توثيق/إعدادات/تقارير)، وخريطة اعتماد الوحدات من استيرادات `require`/`import` النسبية. يُحدَّث الفهرس مع كل تغيير ويُحفظ داخل مساحة العملية (`.loam/swarm/project-index.json`) مع حدث يسجل الفرق، ويُغذّى مكثفًا في مطالبات أدوار التحليل والتنفيذ والمراجعة والتأليف والجودة. الفهرس لا يغادر مساحة عمله، فلا ينتقل سياق مشروع أو أسراره إلى عملية أخرى. عند إنشاء العملية يمكن تمرير `repoSeed` (مسار مجلد مستودع محلي، حتى 1000 ملف) ليُنسخ إلى مساحة المهمة قبل البدء، فتتحول الشركة إلى مهام تعديل وإصلاح على كود قائم.

### الإصلاح الذاتي داخل العملية

رفض بوابة الجودة (دليل تحقق ناقص أو فاشل أو `QA_FAILED`) أو بوابة المراجعة (`REVIEW_ISSUES`) لا يفشل العملية فورًا: يعيد المجدول تشغيل التنفيذ ثم المراجعة ثم الجودة مع تمرير التشخيص الكامل كتغذية راجعة، ضمن ميزانية جولات يحددها الطلب (الافتراضي 2، والحد 0–4). استنفاد الميزانية يفشل العملية ويُبقي التشخيص متاحًا لإعادة المحاولة. أعطال النموذج أو البروتوكول لا تستهلك جولات إصلاح.

بوابة نزاهة إضافية: بين جولات الإصلاح، لا يجوز حذف ملفات الاختبار أو إنقاص عدد حالاتها — بما فيها ملفات الاختبارات المستقلة — وأي تراجع يُعاد كتشخيص إلى التنفيذ ويستهلك جولة إصلاح. تفاصيل القدرات والحدود في `docs/swarm-frontier-progress.md`.

### نقاط حفظ Git والفروق

تُهيّئ كل عملية مستودع Git داخل مساحة مهمتها وتحفظ نقطة تفتيش (commit) بعد اكتمال كل مرحلة، مع `.gitignore` للملفات المستبعدة. في جولات الإصلاح يُسجَّل فرق الكود الفعلي (`git diff --stat`) بين نقطتي تنفيذ كدليل في سجل الأحداث. تعذّر git يعطّل نقاط الحفظ لهذه العملية فقط دون التأثير على التنفيذ.

## الحفظ والإيقاف

يحفظ الخادم حالة التشغيل وسجل الأحداث (بما فيها أحداث جولات الإصلاح ونقاط Git) تحت `data/swarm`، وملفات المشروع وتقارير المراحل تحت مجلد المهمة المعزول. تستعيد الواجهة العملية المختارة بعد تحديث الصفحة، وتعرض لوحة دليل التحقق بأمر التحقق الناجح الفعلي وعدد محاولات آخر جولة جودة وجولات الإصلاح المستهلكة. بعد توقف غير متوقع تُعرض العملية كمتوقفة، ويمكن **استئنافها من نقاط الحفظ** عبر زر «استئناف من نقطة التوقف» أو `POST /api/swarm/runs/:id/resume`، فتعاد المراحل غير المكتملة فقط.

الإيقاف من المساحة أو صفحة المهمة يصل إلى استدعاء النموذج والأدوات. إعادة محاولة التشغيل الفاشل تحتفظ بالمراحل المكتملة؛ عند فشل الجودة تعيد التنفيذ والمراجعة والجودة والتسليم مع تمرير التشخيص. قد تعيد المرحلة غير المكتملة بعض الأوامر السابقة. تعمل عمليات الشركة على مسارين متوازيين مخصصين (مراحلها أدوات ملفات وأوامر ضمن مساحة المهمة فقط ولا تستخدم المتصفح وسطح المكتب المشتركين)، حتى عمليتي شركة نشطتين معًا وحتى أربع عمليات غير منتهية؛ ما زاد يُرفض حتى تنتهي عملية أو تُلغى.

## معنى التحقق وحدوده

يتطلب اكتمال التنفيذ ملفات مصدر حقيقية غير ملفات الاختبار أو التقارير. تتطلب الجودة أمر فحص معترفًا به، منفردًا دون وصل أو إعادة توجيه، مثل `node --test calculator.test.cjs` أو `npm test`. أوامر المساعدة والإصدار والوضع التجريبي لا تعد دليلًا. فشل أمر تحقق لا يختفي بمجرد نجاح أمر مختلف.

تثبت هذه البوابة تنفيذ الفحص ونتيجته، ولا تضمن كفاية التغطية أو جاهزية أي منتج يولّده النموذج للإنتاج. جودة النتيجة تعتمد على النموذج والموجز. تستخدم النماذج المحلية والسحابية المتاحة عبر واجهة Ollama؛ لا يوجد موصل مباشر جديد لمزوّد نماذج آخر. تحليل المخاطر ليس بحثًا حيًا في الإنترنت. مجلد المهمة يعزل الملفات التي تديرها الأدوات؛ تشغيل shell يبقى بصلاحيات التطبيق وسياساته، وليس حاوية نظام تشغيل.

## التحقق من المساحة

```powershell
npm run typecheck
npm run check:swarm
npm run check:swarm-http
npm run check:swarm-ui
npm run check:swarm-bench
npm run check:swarm-security
npm run check:swarm-memory
npm run check:swarm-compare
npm run check:swarm-live
```

اختبار HTTP والمتصفح يستخدم نموذج بروتوكول حتمي مع أدوات ملفات وأوامر حقيقية؛ لا يقيس جودة نموذج لغوي. اختبار `check:swarm-live` اختياري ويستخدم النموذج المضبوط في `config.json`، أو `LOAM_SWARM_MODEL`، وينشئ مهمة برمجية صغيرة في بيانات مؤقتة مستقلة ويحفظ دليل النتيجة في المسار المطبوع.

واجهات API: `GET/POST /api/swarm/runs` (يدعم `stageModels` لاختيار نموذج مختلف لكل دور)، و`GET /api/swarm/runs/:id`، و`POST /api/swarm/runs/:id/cancel` أو `/retry` أو `/resume`، و`GET /api/swarm/runs/:id/artifacts`. بعد نجاح الاختبارات المستقلة يمسح المحرك مساحة العمل أمنيًا (أسرار واعتمادات خطرة) وتُسجل النتيجة في تقرير `security`. طلبات التشغيل من المتصفح تتطلب نفس الأصل وJSON.

## نتيجة التحقق — 18 أكتوبر 2026

### جولة الذاكرة المفهرسة والمستودع القائم (لاحقًا في اليوم)

نجح تشغيلان حقيقيان متتاليان على `glm-5.3-flash:cloud` بالمسار ذي التسعة أدوار: الأول مشروع كامل (واجهة RTL + API + تخزين) بلا جولات إصلاح — 19 اختبارًا فعلًا من الجودة و19 من بوابة المحرك المستقلة (بينها فحص «لا حزم خارجية ولا شبكة في الواجهة» وفحص أن `node server.cjs` ينصت فعلًا عند التشغيل المباشر) ورحلة متصفح كاملة. والثاني **مستودع قائم مزروع** (`repoSeed`) بمهمة إصلاح: حللته مرحلة تحليل المستودع بنموذج فعلي مستندة إلى الفهرس، أصلح التنفيذ العيب أدنى تعديل، وكتب المؤلف المستقل 18 اختبارًا بينها **حراس منع التلاعب** («الاختبارات الأصلية الثلاثة باقية بكاملها»، «util.cjs لم يتغير») — وكلها نجحت من الجودة ومن بوابة المحرك. الذاكرة المفهرسة سجلت 14 ملفًا و3 حواف اعتماد محلية. وخلال محاولات اليوم الحية امتص النظام بنجاح: مهلة مزود (إعادة محاولة 4ث/12ث)، ونفاد خطوات مراحل (بوابة جولة جديدة بميزانية جديدة، وتشغيل نفدت فيه خطوات «المتطلبات» أثبت الحاجة لإعادة المرحلة التحليلية نفسها فأُصلح)، ومحاولة التفاف عبر `node -e` كشفتها وسدتها بوابة البصمات.

### جولة التحقق المستقل ورحلة المستخدم (لاحقًا في اليوم)

نجح تشغيل حقيقي رابع على `glm-5.3-flash:cloud` بالمسار الكامل ذي الثمانية أدوار: منتج كامل (واجهة عربية RTL + API + تخزين ذري + README). كتب مؤلف الاختبارات المستقل 11 اختبار قبول فعليًا تغطي كل معايير القبول وموانع المراجعة، بينها مصفوفة مسارات HTTP كاملة، وعقد الواجهة الأمامية (ترابط add/toggle/delete بالـAPI)، وعنصرية الكتابة (لا ملف مؤقت متبقٍ)، وإثبات أن `require` للخادم لا يفتح منفذًا. نفذت الجودة `node --test acceptance.test.cjs` بنجاح، ثم نفذت **بوابة المحرك المستقلة** الملف نفسه بـ`--test-force-exit`: 11/11 ناجحة. بعدها شغّل الاختبار الحي المنتج المُسلَّم فعليًا وقاد من متصفح حقيقي رحلة مستخدم كاملة: فتح الصفحة ← إضافة مهمة ← إعادة تحميل تثبت التخزين ← تبديل الحالة (فئة done) ← حذف مع اختفاء العنصر. الأدلة: `journey.png` و`journey.json` و`live-result.json` في مجلد الدليل المؤقت للاختبار. جولتان سابقتان في اليوم نفسه وثقتا سلوك الإصلاح الحي (جولة مراجعة أعادت التنفيذ مرة)، وعولج بعد تشخيصهما تعليقُ اختباراتٍ تفتح خوادم عبر بوابة المهلة/الإجبار الموصوفة في وثيقة التقدم.

نجحت تجربة فعلية على `glm-5.3-flash:cloud` عبر المراحل الست، وأنتجت `calculator.cjs` و`calculator.test.cjs` ونفذت `node --test calculator.test.cjs`: ثمانية اختبارات ناجحة دون فشل. الدليل محفوظ في `output/verification/swarm-live/result.json` مع الملفات الناتجة. هذه تجربة صغيرة محددة، وليست قياسًا عامًا لقدرة النظام على أي مشروع.

نجحت اختبارات المحرك (بما فيها بوابات المراجعة والجودة وجولات الإصلاح المقيدة)، وHTTP والمتصفح بسبعة أدوار ولوحة دليل التحقق، والحفظ بعد إعادة التشغيل، ورفض الطلبات من أصل مختلف، والإلغاء، وإعادة المحاولة، وعرض الهاتف. نجحت أيضًا TypeScript، وفحص الترميز، وعزل الأنماط، والاستعادة، واختبارات التنسيق القائمة، وبناء الخادم.
