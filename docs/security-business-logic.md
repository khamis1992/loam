# Business logic replay, idempotency, quota, step-order, pricing, cancel, race and consistency verification — revision 47

Campaign assessments accept seven explicit business logic case lists, all fed by one `businessSecrets` map of fresh per-run values (JSON bodies ≤ 8192 bytes each; plain-string declared values for consistency cases; never persisted in findings or evidence text):

- `business` — replay/idempotency cases (up to five): each declares one exact in-scope POST `path`, a `bodyRef`, a GET state witness (`statePath` + `statePointer` JSON Pointer resolving to a finite number), the nonzero integer `stateDelta` one execution must apply, and `replays` (1–3 identical resubmissions).
- `businessQuotas` — usage-limit cases (up to five): the same witness model plus a declared `limit` of 1–20 allowed executions.
- `businessSteps` — step-order/prerequisite cases (up to five): an ordered list of 2–6 steps ending in the protected final step. A step with `bodyRef` executes as POST; a step without one executes as GET. The same state witness measures the final step's declared effect.
- `businessPricing` — price/discount/credit cases (up to five): a POST operation whose declared expected amount (`stateDelta`, a nonzero integer in minor units up to 10^12) must move the numeric witness by exactly that amount.
- `businessCancels` — cancel/refund/rollback cases (up to five): a state-changing POST (`operationPath` + `operationBodyRef`) followed by its declared cancel/refund request (`cancelPath` + `cancelBodyRef`). `expectedCompensation` declares the witness movement a correct rollback applies — full reversal by default, or an explicit partial compensation (for example a restocking fee); amounts are minor-unit integers up to 10^12.
- `businessRaces` — concurrency/race cases (up to five): identical POST submissions (`concurrency` 2–4) released simultaneously at one operation whose declared execution bound is `allowed` (1–concurrency, default 1).
- `businessConsistency` — layer-consistency cases (up to five): 2–3 GET layer definitions (`layers`, each an exact scoped path plus a JSON Pointer) and one declared known value (`valueRef`). Every layer must resolve its pointer and reproduce the declared value exactly; at least one matching layer (the positive control, typically the authoritative record view) is required before any divergent layer is reported.

Execution order per replay case: read state → submit once → read state (positive control: the declared delta must apply exactly) → replay the identical body → read state again. All requests share the campaign budget, scope, delay and evidence log; POST evidence carries `postPolicy` and `requestBytes` like the browser engine.

Quota case execution: read state → submit `limit` times, reading state after each (every control submission must apply the declared delta) → one further identical submission → read state. If the server rejects a control submission before the declared limit, the case is inconclusive with the hint that the enforced limit may be lower than the declared one; adjusting the declaration is an operator decision, never inferred silently.

Step case execution: read state → run the bypass probe (only the final step, against a fresh state where no declared prerequisite ran) → read state. If the witness advanced by the declared delta, the final step applied without its prerequisites (`observed`, `business_step_<case-hash>` finding) and the ordered control sequence is skipped to avoid repeating side effects. Otherwise the full ordered sequence runs as the positive control: if it applies the declared delta while the lone final step was rejected or had no effect, the prerequisite state machine held (`not_observed`); if the ordered sequence is itself rejected or the witness does not match, the case is `inconclusive` and proves nothing either way.

Pricing case execution: read state → submit the priced operation (must be accepted) → read state. The actual movement must equal the declared expected amount exactly. The measurement controls are the accepted request plus a non-zero witness movement (which proves the witness responds to this operation); a zero movement is inconclusive because a zero-charge defect and an unresponsive or misdeclared witness cannot be distinguished. A movement in the opposite direction of the declaration (for example a credit instead of a charge) is reported with explicit direction evidence.

Cancel case execution: read state → submit the operation (must be accepted and apply its declared delta — the positive control) → submit the cancel/refund → read state. The compensation movement must equal `expectedCompensation`: full rollback restores the witness to its pre-operation value; a declared partial compensation must match exactly. An accepted cancel with a different movement (kept charges, partial, double or reversed refunds) and a rejected cancel that still moves state are findings; asynchronous settlement can show the same signature as an accepted-but-unsettled refund, so verify final settlement before acting. A rejected cancel with no state change is inconclusive — a policy answer, not a proven defect — and a correct compensation applied under a rejection status is not a defect.

Race case execution: read state → reserve every burst ticket through the paced budget → release the identical submissions simultaneously (so they genuinely overlap in flight) → read state. The number of whole executions measured through the witness must not exceed `allowed`. A bound exceeded under concurrency is direct evidence that the enforcement is not atomic; a bound that held under one burst is timing-dependent evidence, not proof of safety. If every submission is rejected and nothing applies, the case is inconclusive because it never established that a valid execution is possible.

Consistency case execution: fetch each declared layer in order and resolve its pointer. Strings compare exactly; finite numbers compare via their exact decimal string form. The declared value itself is never recorded — only per-layer statuses, match booleans and value kinds. Verdicts: every layer resolved and matched → `not_observed`; the control matched while another resolved layer differed → `observed` divergence finding; no layer reproduced the declared value → inconclusive (verify the expected value and freshness); some layers unresolvable (unavailable, invalid JSON, missing pointer, unsupported type) with no divergence → inconclusive, because consistency across every declared layer is unverified.

Outcome rules:

- `observed` — replay: the control held and replay re-applied the operation (state advanced by further whole deltas), emitting a `business_replay_<case-hash>` finding (medium). Quota: all control submissions applied and the one excess submission advanced the state witness beyond the declared limit (whether it returned 2xx or an error), emitting a `business_quota_<case-hash>` finding (medium). Steps: the lone final step applied the declared delta on a fresh state, emitting a `business_step_<case-hash>` finding (medium). Pricing: the witness moved by a different amount than declared (or in the opposite direction), emitting a `business_pricing_<case-hash>` finding (medium). Cancel: an accepted cancel/refund moved the witness by an amount other than the declared compensation, or a rejected request still changed state, emitting a `business_cancel_<case-hash>` finding (medium). Race: concurrent submissions produced more whole executions than the declared bound, emitting a `business_race_<case-hash>` finding (medium). Consistency: a resolved layer exposed a different value than the declared one while the control layer matched, emitting a `business_consistency_<case-hash>` finding (medium). Impact wording stays operation-relative (duplicate orders/charges; extra free credits, votes or trials; shipping, payout or approval effects reached before their prerequisites; overcharges, undercharges and inverted credits or refunds; kept charges after promised refunds, partial, double or unauthorized reversals; multi-claimed single-use resources under concurrency; stale or divergent views between UI, server and record layers).
- `not_observed` — replay: replay accepted without effect, or every replay rejected as a duplicate (409/422). Quota: the excess submission rejected (403/409/422/429) or returned another status without applying the operation, and the state witness did not advance. Steps: the final step alone was rejected or had no effect, and the full ordered sequence applied the declared delta. Pricing: the witness moved by exactly the declared amount. Cancel: the compensation matched the declared amount (including a correct compensation applied under a rejection status). Race: the declared bound held under the concurrent burst. Consistency: every declared layer resolved its pointer and reproduced the declared value exactly.
- `inconclusive` — state witness unavailable, first submission (replay) or any control submission (quota) not accepted, control delta mismatch, an unexpected state change during the bypass probe, a pricing operation accepted without moving the witness, a cancel/refund rejected without a state change (policy answer), a race burst where every submission was rejected and nothing applied, a consistency case where no layer reproduced the declared value or some layers could not be compared, transport failure, a non-integer final delta, or per-case request-budget exhaustion (the engine records the case as inconclusive instead of crashing the campaign). Inconclusive cases mark the run `partial`, add a `business_coverage` error finding, keep the diagnostics module `incomplete` with an Arabic reason, and never count as evidence of idempotency, quota enforcement, prerequisite protection, pricing correctness, rollback fidelity, concurrency safety or layer consistency.

Retest behavior: all seven case lists and their value digests are pinned in the campaign witnesses; a retest demands fresh values that hash to the same digests and preserves the case lists, so a repaired operation can move the finding to `notObserved` while an untestable one stays `unverified`. Reports include a "Business logic verification" section with all proofs.

Honest limits:

- Each case executes the declared operation (1 + replays times, limit + 1 times, the bypass plus possibly the ordered sequence, or one priced submission) inside the authorized scope; records created by the test may persist (test-data cleanup remains an open platform gap).
- A clean replay proves idempotency for the declared body only, a clean quota case proves enforcement of the declared limit for this identity and body only, and a clean step case proves the declared final step depends on the declared prerequisites for this body — not for concurrent submitters, other identities, window resets or undeclared intermediaries (an application may enforce steps the case never declared, so a bypass finding is relative to the declared sequence).
- The step bypass probe assumes a fresh state: prerequisite state left by earlier cases in the same campaign can mask a bypass; order cases accordingly.
- A pricing mismatch compares the server's arithmetic against the operator's declared expectation; the platform does not derive the correct price itself. Verify the currency, minor-unit scale and the declared model before acting on a finding. The same applies to cancel compensations: the declared rollback model (full or partial) is the operator's declaration.
- Asynchronous settlement can make an accepted-but-unsettled refund look like a short refund; verify final settlement before acting on a cancel finding.
- The state witness must be chosen by the operator; a counter that coalesces multiple effects, saturates, or is eventually consistent can produce inconclusive or misleading deltas, which the integer-delta rule rejects rather than guesses.
- A clean race case is timing-dependent: a bound that held under one burst does not prove atomicity under different interleaving, load or replicas. A race finding, conversely, is direct evidence that the bound is not enforced atomically for that window.
- Consistency comparison is point-in-time over GET views: transient replication lag can look identical to a stale-view defect, numbers compare via their decimal string form (formatting such as leading zeros or localized decimals will not match), and only the declared pointers are compared — divergence in undeclared fields is not tested.
- Same-origin cases only in this revision; cross-origin business cases via API grants are not implemented.
