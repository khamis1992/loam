# Explicit API-probe CORS verification — revision 39

Playwright interception can expose fulfilled API responses that a normal cross-origin fetch would reject. Revision 35 added explicit CORS checks to anonymous collection probes, but the account matrix still relied on browser enforcement. That could turn an unreadable response into apparent positive-control or authorization evidence.

The explicit cross-origin account-matrix contexts now verify CORS independently. Their configured fetches use `credentials: include`, so both preflight and final response must allow the exact frontend origin and contain `Access-Control-Allow-Credentials: true`. Wildcard origin or wildcard allowed headers cannot grant those credentialed requests. Authorization must be explicitly named even for noncredentialed requests. Anonymous probes retain `credentials: omit` behavior and share the helper.

The router derives non-safelisted request-header names from the headers it will actually forward. A budgeted, timed, redirect-rejecting OPTIONS request is sent first when needed, without cookies or authorization. A rejected preflight prevents the GET/POST request; a rejected final response is not fulfilled into the page. POST with JSON requires permission for content-type as well as authorization. OPTIONS bodies are deliberately omitted. Evidence includes per-account request IDs, `corsAllowed`, the credentials mode and requested header names; header values and response bodies remain omitted.

GET, HEAD and POST are CORS-safelisted methods, so a preflight triggered by headers need not explicitly list those methods in `Access-Control-Allow-Methods`. The checks follow the [WHATWG Fetch CORS protocol and credentials rules](https://fetch.spec.whatwg.org/#cors-protocol-and-credentials) and [non-wildcard authorization-header rule](https://fetch.spec.whatwg.org/#cors-non-wildcard-request-header-name). This implementation is bounded to the explicit probe inputs, not a complete reimplementation of Fetch, its preflight cache, cookie policies or browser-specific networking behavior.

`src/scripts/check-security-cross-accounts.ts` now supports source and installed-service execution. Real Chrome fixtures verify GET/POST exposure baselines, direct-denial retests, identity/session failures, missing CORS origin, missing credential permission, wildcard origin/headers, rejected authorization preflight, missing preflight credential permission and rejected JSON content-type. Assertions check that rejected preflight never sends the protected GET/POST, OPTIONS contains no credentials, evidence records its credentials mode, and baseline fingerprints remain unverified on communication failure. Anonymous collection regressions also passed with the shared helper. Full-project typecheck and server build passed.

Revision 39 was installed on Loam 0.5.23, preserving the profile and 124 tasks, with all four runtime/UI files matching the staged candidate. Backup: `output/verification/security-runtime-backup-20261018-145951`.

The complete cross-origin regression also passed against the installed service using `LOAM_SECURITY_TEST_BASE=http://127.0.0.1:3939`. Its persisted task is titled `Cross-origin CORS account regression`; campaigns retain the baseline, negative communication cases and GET/POST retest comparisons. This verifies deployed endpoints and the new CORS evidence fields rather than source imports alone.

Scope limit: general application-generated API traffic outside these explicit probe contexts still relies on intercepted browser behavior and has not received this explicit verifier. Its CORS readability must not be inferred from a successful fulfilled response alone. UI layout and configuration remain the existing API grants/account matrix. No production service or Nutrio data was mutated for these local fixtures; the feature does not establish frontier-level or universal remediation capability.
