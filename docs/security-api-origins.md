# Explicit API origins

Browser assessments now accept `browser.apiGrants`. These are separate from frontend discovery seeds. Keep the frontend scope on one origin. Each grant permits only an exact API origin, exact paths and selected GET/HEAD/POST methods; OPTIONS preflight is permitted only for a granted method and path.

```json
{
  "apiGrants": [{
    "origin": "https://api.example.test",
    "paths": ["/auth/token", "/records"],
    "methods": ["GET", "POST"],
    "credentialHeaders": ["authorization", "apikey"]
  }]
}
```

The API receives only selected credential headers already generated by the application. Supplied frontend bearer/cookie values and account bearer overrides are never injected into API-origin requests, including when the origins share a hostname but differ in port. With an empty `credentialHeaders` list, application authorization/cookie/API-key headers are removed. The router does not synthesize permission to read cross-origin responses. Interception can nevertheless bypass normal browser CORS enforcement; explicit anonymous and account-matrix probes now perform additional checks described in `security-account-cors.md`. General application traffic is not yet covered by that explicit verifier.

API grants do not permit documents, iframe navigations, scripts, images, WebSockets or API redirects. POST body size remains bounded at 64 KiB and all requests use the campaign budget. Response evidence omits bodies and query values. No service-role credentials are required. The UI rejects configured API grants on a runtime older than revision 6.

Limits: origins are request-access grants, not support for cross-origin UI login pages or OAuth popups. Exact API resource identifiers can be provided as paths; this does not automatically enumerate or generate record identifiers.

## Cross-origin account matrix (runtime revision 7)

Add `apiCredentials` to each account. Header values below are secret references, never literal tokens. The temporary value for `aliceToken` includes `Bearer ` when required by the API. A cookie-based API may use empty headers, with `cookie` explicitly granted and cookies established by that account's login flow.

```json
{
  "apiCredentials": [{
    "origin": "https://api.example.test",
    "headers": {"authorization": "aliceToken", "apikey": "testPublicKey"},
    "identityRef": "aliceApiId"
  }]
}
```

An API authorization case specifies its own origin and an identity endpoint returning a top-level string field. Both identity and protected-record paths need explicit GET grants. For example:

```json
{
  "id": "record_A",
  "kind": "api",
  "path": "/records/fixture-a",
  "api": {"origin": "https://api.example.test", "identityPath": "/auth/user", "identityField": "id"},
  "markerRef": "recordAMarker",
  "allowed": ["alice"],
  "denied": ["bob"]
}
```

Each account must have a distinct expected API identity. The frontend witness and API identity must both remain valid before and after testing. A 401/403 on the record is a valid denial only when the identity endpoint still verifies the account and the allowed-account control succeeds. API credentials stay scoped to the explicit test fetches and identity checks; they are not global browser headers. Expected API identities are hashed and pinned for retesting, as are frontend identities and protected markers. Replacing the identities requires a new baseline.

Verification commands:

- `npm run check:security-api-origins`
- `npm run check:security-cross-accounts`
- `npm run check:security-flows`
- `npm run check:security-http`

The fixture runs local frontend and API servers in isolated browser sessions. It verifies JSON POST and authenticated GET, global credential containment, denied routes/methods/redirects, redaction, and unchanged grants on retest. No Nutrio cloud project was scanned by these tests.
