# مهارة الفريق الأحمر (red-team) — اختبار الاختراق المصرّح به فوق Loam

## الضوابط الإلزامية (لا تُتجاوز)
1. **نطاق مملوك أو مصرّح فقط**: لا تفحص ولا تهاجم إلا أنظمة يملكها المستخدم أو لديه تفويض كتابي صريح بها. إذا لم يذكر المستخدم تصريحًا صريحًا فاسأل قبل أي إجراء.
2. **الوضع الافتراضي localhost**: بدون سجل تفويض `AUTHZ-####` لا يمكن الوصول إلا إلى `127.0.0.1`/`localhost`/`::1`، والأفعال التخريبية ممنوعة. أي هدف خارجي يحتاج `authzId` بعد إنشاء سجل تفويض صالح.
3. **لا نتيجة بلا برهان**: كل ثغرة تُذكر كنتيجة مؤكدة يجب أن تكون قد عبرت بوابة الأدلة `evaluateEvidenceGate` (طلب/استجابة مُلتقطة أو ملاحظة PoC). لا تروّج لمخرجات ماسح خام على أنها اختراق مؤكد؛ ما لا يُثبت يُصنّف `unverified`.
4. **التخريبي موافقة بشرية**: `--dump`، الأوامر المدمرة، حذف/تعديل حالة الهدف، وحقن أدوات كتابة تتطلب موافقة صريحة من المستخدم، وتُدوَّن في سجل التدقيق.
5. **مفتاح الإيقاف والأسرار**: عند طلب الإيقاف الفوري استخدم مفتاح الإيقاف (`engageKillSwitch`). لا تطبع أسرارًا في المخرجات؛ التدقيق يخفي ترويسات المصادقة والكوكيز تلقائياً.

## الأدوات والسكربتات المتاحة
| الأداة/السكربت | الوظيفة |
|---|---|
| `red_campaign` | حملة واحدة على هدف مصرّح: يكتب `red/<campaignId>/report.md` و`sarif.json` و`poc/*.json` في مساحة العمل |
| `red_report` | يعيد فتح تقرير حملة سابقة من `red/<campaignId>/report.md` |
| `npm run red:engines` | تثبيت/تحديث nuclei, ffuf, ysoserial, sqlmap في `~/.loam/tools` مع SHA256 |
| `npm run red:engage` | اشتباك حقيقي بالمحركات + سجل `docs/red-team-engagements/ENG-...` + مقارنة retest مع الاشتباك السابق |
| `npm run test:red` | حزمة الاختبارات الحمراء (وحدة + تكامل) |
| `npm run check:red` | قبول مخبري ذاتي الاحتواء (ثغرة SSRF مزروعة + اختبارات الأمان السلبية) |

## خطوات العمل القياسية
1. **تهيئة المحركات (مرة واحدة)**:
   - عند غياب المحركات أو قبل أول حملة: نفّذ `npm run red:engines`.
   - يُثبّت nuclei/ffuf/sqlmap/ysoserial تحت `~/.loam/tools` ويكتشفها الجسر تلقائياً.
   - ZAP اختياري (يثبّت منفصلًا)، وcaldera/freeway مخبريان فقط.
2. **تحديد الهدف والتفويض**:
   - محلي: استخدم `red_campaign` مع `target` مثل `http://127.0.0.1:3000` بدون `authzId`.
   - أوسع من localhost: أوقف، واطلب من المستخدم إنشاء سجل تفويض أولًا (`createAuthorizationRecord` + `saveAuthorization`) ثم استخدم `authzId: "AUTHZ-0001"`.
   - مصادَقة: مرّر `--auth bearer:<token>` أو `--auth cookie:<...>` في `red:engage` (أو `auth` في الاستدعاء البرمجي).
3. **التخطيط (اختياري)**:
   - افتراضيًا الحملة قواعد حتمية.
   - عند طلب تخطيط ذكي: `red_campaign` مع `plan: "auto"` أو `npm run red:engage -- --plan auto`؛ يقترح النموذج ادعاءات اختبار وكلها تبقى مقيَّدة بالبوابة والأدلة.
4. **تنفيذ الحملة**:
   - `red_campaign` لهدف واحد، أو `red:engage` لسجل اشتباك دائم ومقارنة retest.
   - المحركات المتاحة تُدرَج تلقائياً (SQLi/DAST/ffuf/nuclei/ysoserial) + وحدات SSRF داخلية؛ ما لا يوجد محرك له يبقى `inconclusive` وليس نتيجة.
5. **قراءة النتائج وتقديمها**:
   - اقرأ `report.md` و`sarif.json` و`poc/<findingId>.json`.
   - لكل نتيجة مثبتة: الخطورة، الهدف، الدليل EV، PoC قابل للإعادة، والإصلاح المقترح.
   - اعرض أيضًا قسم `unverified` بأسباب الحجب (نفي أمين، عدم توفر محرك، موافقة مرفوضة).
6. **التقييم والتقوية (O-5)**:
   - `red:engage` يكتب `latest.json` ويقارن مع الاشتباك السابق (new/persistent/notObserved/unverified).
   - لإصدار مهام تقوية زرقاء للنتائج المثبتة فعّل `openHardeningTasks` في بناء التقرير (اختياري ومعطّل افتراضيًا).
   - عند إصلاح ثغرة كشفتها الحملة، أعد `red:engage` للتحقق من زوالها عبر retest.

## أمثلة جاهزة
- «شغّل red_campaign على http://127.0.0.1:3000 واعرض النتائج المثبتة فقط مع روابط PoC.»
- «ثبّت المحركات ثم نفّذ red:engage على http://127.0.0.1:3939 مع --nuclei-tags cve ولخّص الفرق عن الاشتباك السابق.»
- «خطط تلقائيًا لحملة على تطبيقنا المحلي (plan:auto) وأبلغني بما لم يُثبت ولماذا.»

## لا تفعل
- لا تستهدف الإنترنت أو أطرافًا ثالثة أو نطاقات عامة ولو بدا الهدف بريئًا.
- لا تعتبر 401/403 دليل اكتشاف ثغرة بذاته؛ فهو غالبًا حاجز مصادَقة طبيعي.
- لا تستخدم `--os-shell` أو `--dump` أو أدوات إزالة الأثر إلا بموافقة بشرية صريحة وعلى مخبر مملوك.
- لا تنسخ أكواد GPL/AGPL داخل Loam؛ المحركات تبقى عمليات خارجية عبر الجسور.
