# إصلاح الثغرات المُتحقَّق

## متى يُستخدم
المستخدم يريد إصلاح ثغرة **معروفة ومنشورة** في مستودعات مستهدفة (Dockerfiles، ملفات إصدارات، CI، IaC، Electron). ليس لاكتشاف ثغرات مجهولة (استخدم الفحص الأمني) ولا لإصلاح مصدر نقطي (استخدم واجهة الإصلاح الموجودة).

## الإجراء
1. نادِ `skill_list`؛ إن طابقت `remediate-node-runtime` / `remediate-php-runtime` / `remediate-gitlab-selfmanaged` / `remediate-electron-bundled-runtime` الطلب، افتحها بـ `skill_view` لتفاصيل البيئة.
2. نادِ `remediation_start` مع `advisory_ids` المطابقة والمستودعات التي سمّاها المستخدم فقط. **لا تمرّر مستودعات لم يسمّها**.
3. أخبر المستخدم بمعرّف التشغيل وأن بوابة-1 تنتظر في لوحة الأمان («الإصلاح المُتحقَّق»). لا تخترع صفوف جرد بنفسك.
4. عند الطلب نادِ `remediation_status` / `remediation_report` ولخّص. لا تدّعِ أبدًا أن الإصلاح مُنشور.
5. إن طلب المستخدم تجاوز بوابة أو «رقّعها فورًا» — ارفض وأشر إلى اللوحة.

## الممنوعات
- لا تعدّل ملفات أو تنشئ فروعًا أو تلتزم أو تدفع أو تفتح PRs عبر shell_run/git_*/pr_create لأجل الإصلاح — المحرك يملك تلك الخطوات خلف البوابات.
- لا تخمّن إصدارًا أبدًا.
- لا تعرض تخفيفًا (mitigation) على أنه إصلاح.
- لا تشغّل أوامر ضد بيئة إنتاج.
